In March, I wrote a long post (which you *really* should read) about Artificial Intelligence and our ever changing future. Although that post gave an overview of what impact that this technology could have and what we should do, it didn’t really explore the impact on roles other than software development. It’s not easy or comfortable exploring the possibility if AI *could* do your job, but I feel that it’s a conversation that is going to have to happen sooner than later. So here I am, wondering if AI could take my role in Software Testing.

So I decided to embark on a brief journey to explore just that.

## The tools

For this, I am using Claude Code as my primary tool. It’s powerful, ever improving, and is seen as a decent tool when it comes to AI.

I did create a QA strategist agent within Claude Code, so that this agent was an expert and solely focused on QA activities. Here’s how Claude Code describes this particular agent:

> Designs test plans and strategies, reviews code for quality issues, analyzes coverage, and identifies bugs/regressions. Use proactively after significant changes.
> 

Sounds like a suitable agent for QA activities in my view, this will be the agent that will be used throughout this experiment.

## The application used for testing

I used Claude Stocks App for this experiment. This is a good application for looking at multiple user journeys and interacting with different elements (text boxes, buttons, graphs, etc).

## Exploratory testing

I’ve worked at places that have had gigantic regression packs, that cover specific user journeys, that were run against each release. Problem is with these tests is that they lose their effectiveness over time. What I mean by this is that the same set of tests don’t continue to find new defects. So exploratory testing is a great way in discovering new defects that a small amount of users might experience, and think of tests that normal testing hasn’t covered.

So this is what I instructed the agent to do, just do some exploratory testing, don’t write any new tests and report the results back to me. This is what the agent found:

> 
> 
> 
> **QA Exploratory Test Summary — Claude Stocks App (`main` branch)**
> 
> The QA agent completed a thorough exploratory pass against `main`. No new tests were written; the existing E2E suite (34 specs) was run and passed, but the pass uncovered several runtime bugs the suite doesn't cover.
> 
> **Top Findings (full report from agent)**
> 
> **Critical**
> 
> - **C-01 — `BRK.B` ticker crashes the dashboard.** Clicking BRK.B in the TickerTape navigates to `/dashboard?symbol=BRK.B`, the symbol gets stripped to `BRKB`, Finnhub returns `null` for `d`/`dp`, and `formatChange(null)` throws an unhandled `TypeError`. There's no error boundary, so the whole page goes blank. Root cause: `TICKERS` in `/app/api/stock/movers/route.ts` allows dotted symbols, but `SYMBOL_RE` doesn't.
> - **C-02 — Dashboard accepts garbage symbols (`?symbol=123`).** Numeric-only or special-char symbols pass the empty-string redirect, get sanitized to `""`, and every child component renders a permanent error state with no recovery.
> 
> **High**
> 
> - **H-01 — "Search" button silently does nothing on no-results.** Button stays enabled, click is a no-op, dropdown disappears — two stacked silent failures.
> - **H-02 — No length cap on `/api/stock/search?q=`.** A 5 000-char query forwards to Finnhub and returns HTTP 500 instead of a 400.
> 
> **Medium**
> 
> - **M-01** — `FinnhubQuote.d`/`dp` typed as `number` but Finnhub returns `null`; underlies C-01.
> - **M-02** — No per-symbol `<title>` on the dashboard page (no `generateMetadata`).
> - **M-03** — Search input lacks proper combobox ARIA pattern; arrow-key navigation in results dropdown not implemented (WCAG 1.3.1 / 4.1.3 failure).
> - **M-04** — `lib/session.ts` accesses `sessionStorage` without an `isClient()` guard (latent SSR fragility).
> 
> **Low**
> 
> - **L-01** — Brand inconsistency: "Claude Stocks App" vs "Claude Stocks".
> - **L-02** — News `image` field is fetched and sanitized but never rendered (dead weight).
> - **L-03** — Oversized query returns 500 instead of 400 (HTTP semantics).
> - **L-04** — Chart `<canvas>` has no symbol-specific `aria-label`.
> 
> **What Was Tested**
> 
> Homepage render, all six API routes (with exhaustive input probing — empty, special chars, injection, non-Latin, very long strings, lowercase, dotted, invalid), dashboard rendering paths, quote `null`-field edge cases, search UX, candles range switching, security headers, CORS, rate limiter presence, `.env` gitignore check, ARIA on interactive components, the full 34-spec E2E suite, and code review of every search/dashboard/chart/news component.
> 
> **What Was NOT Covered**
> 
> Mobile viewport at 375px (Tailwind responsive classes not visually verified), live browser interaction (curl + code review only — no Playwright UI session was driven manually), market-open polling path (market currently closed), real `sessionStorage` exhaustion, back/forward race conditions, performance profiling (LCP/CLS/TTI), cross-browser (Chromium only), watchlist at the 20-item cap.
>

This is a good example of what I mean by the benefits of exploratory testing. Those two critical issues aren’t covered in the normal automated tests. Now we can add those issues (and everything else that was discovered) to our backlog to be fixed later.

However, the agent did report that these were tested by not using a live browser. Ideally, we would want to use a live browser to mimic what a user would do. It’s also a reason why I like using the automated testing tool Playwright.

## Using a web browser

So, can Claude spin up a web browser and start interacting with the stocks application? The answer is yes, it can do so in the Claude desktop application. It doesn’t test across multiple browsers but if you wanted to see the agent interact with your application and see how it performed against features that were in development, then it’s not a bad idea to see how a user could potentially interact with your software. One thing to keep in mind is that it is painfully slow to watch.

Here are the results from the agent when it used the browser:

> 
> 
> 
> **Live Browser QA — Results**
> 
> The agent drove a real browser via Claude Preview. Highlights:
> 
> **All four prior bugs reproduced live**
> 
> - **C-01 BRK.B crash** — confirmed: Next.js error overlay on `formatChange` calling `.toFixed()` on `null`.
> - **C-02 garbage symbol** — confirmed and refined: actually crashes with a Radix `<Select.Item value="">` error, not just a "broken state". Trips on both `?symbol=123` and `?symbol=!!!`.
> - **H-01 silent search** — confirmed: zero feedback, API call fires and returns empty.
> - **M-03 keyboard nav** — confirmed and **worse than reported**: ArrowDown, Enter, **and Escape** all do nothing in the dropdown. Keyboard users can't select OR dismiss.
> 
> **New bugs only visible in a real browser**
> 
> **High**
> 
> - **N-01 — sessionStorage poisoning persists the crash.** Visiting `/dashboard?symbol=123` writes an empty string into `recentSymbols`. **Every subsequent dashboard visit then crashes** (including valid ones like `?symbol=AAPL`) until the user manually clears sessionStorage. This is the most serious finding of the live pass — one bad URL bricks the app for the whole session.
> - **N-02 — Quote poller runaway.** A single AAPL dashboard load fires `/api/stock/quote` **26+ times**, eventually triggering the app's own rate limiter (429). Polling isn't respecting the cache TTL or is being reset by re-renders.
> 
> **Medium**
> 
> - **N-03** — Profile endpoint fetched twice per page load (two effects fetching the same data).
> - **N-04** — Candles request gets `ERR_ABORTED` then refires; chart renders on the retry but every load doubles candle traffic.
> - **N-05** — Mobile tap targets below the 44 px accessibility minimum: chart range buttons (24 px tall), watchlist star (32×32), company selector & view buttons (36 px).
> 
> **Low / Nit**
> 
> - **N-06** — No visible focus ring on search input or Search button (`outline: none`, `box-shadow: none`).
> - **N-07** — Chart `<canvas>` has `aria-label={null}` — screen readers see an unlabelled image.
> - **N-08** — Chart only 705 px wide on a 1440 px desktop; lots of unused margin.
> - **N-09** — ~350 px of dead space above the search input on mobile (vh-centering on a short viewport).
> 
> **Coverage this pass**
> 
> - **Viewports**: 1440×900, 1280×720, 768×1024, **375×812**.
> - **Flows**: homepage → search → dropdown, nonsense search, BRK.B tape click, garbage-symbol URLs, AAPL dashboard, back/forward, paste 2000-char query, fast-type-then-delete, keyboard nav, mobile tap-target measurement.
> - **Captured**: live console errors (overlay stack traces), full network panel.
> - Dev server stopped cleanly.
> 
> The **N-01 sessionStorage poisoning** chain is the headline finding — it turns C-02 from a one-off crash into a session-wide outage. Worth prioritizing alongside C-01.
> 

It’s interesting that new defects were found when using a live browser and shows that interacting with the browser makes it worthwhile. Plus, we can use this to generate new Playwright tests for us.

So, we know it can spin a browser which is good, but let’s take a look at what happens when I asked it to mimic some user journeys in the live browser?

> 
> 
> 
> **Live User Journey QA — Highlights**
> 
> The QA agent walked five personas through real flows in a real browser. Five takeaways stand out:
> 
> **Per-persona scorecards**
> 
> | **#** | **Persona** | **Goal** | **Score** | **Verdict** |
> | --- | --- | --- | --- | --- |
> | 1 | **Sarah** — first-time desktop user | Find AAPL price + 1Y chart | **5/5** | Smooth, but watchlist toggle is invisible (no toast, just an icon color change) |
> | 2 | **Devon** — power user, split view | TSLA vs NVDA side-by-side | **4/5** | Rate-limit runaway blocks prices for ~30s; second-panel auto-fills "most recent" with no UI to choose NVDA — must edit the URL |
> | 3 | **Aiko** — mobile commuter | 30-second MSFT check | **3/5** | Rate-limit eats half her time; range buttons are 24 px (measured) — untappable on a moving train |
> | 4 | **Rob** — fat-finger typist | Find AMZN despite typos | **4/5** | "amazn" → silent dead end. URL paste, empty submit → identical silence |
> | 5 | **Priya** — BRK.B holder | See Berkshire B price | **1/5** | Raw Next.js error overlay, no fallback, browser-back doesn't escape, and the "BRKB" chip persists in the dropdown as a re-crash landmine |
> 
> **New findings this pass added**
> 
> 1. **The C-02 sessionStorage bug story has been corrected.** Prior pass said BRK.B stored `""` (causing the Radix empty-value crash). Live observation: it actually stores `"BRKB"` (dot stripped). The Radix path may be fixed, but **"BRKB" itself is now a persistent crash vector** — it sits in the recently-viewed dropdown forever, and every click re-triggers C-01.
> 2. **Browser-back doesn't escape the crash overlay.** A normal user hitting back stays trapped on the dev error screen. Most casual users will close the tab.
> 3. **Tap targets measured precisely** (via `getBoundingClientRect`): range buttons **24 px**, watchlist star **32 px**, recently-viewed chips **34 px**, company selector / View button **36 px**. Only the Search button (48 px) clears 44 px. This is a design-system-level gap, not isolated.
> 4. **First-search inconsistency:** "Apple" jumped straight to the dashboard (no dropdown); "Microsoft" showed a dropdown. Real users will be confused about whether they're supposed to pick from a list.
> 5. **Rate-limit runaway is not just a network panel curiosity** — it presents as a visible "Too many requests — retry in 29 seconds" banner blocking the price card on **every** fresh dashboard load. This is the highest-frequency defect in the app.
> 
> **Cross-cutting patterns**
> 
> - **Silent failure** is the dominant UX bug. Mistype, paste a URL, hit empty Enter, click the star — the app gives no feedback in any of those cases.
> - **The rate-limit polling bug touches every persona.** Devon, Aiko, and implicitly every first-time dashboard visitor.
> - **One bad ticker poisons the session.** The BRKB chip survives in the dropdown and the user has no way to know it'll crash them again.

This is good, and interesting to see that the ticker on the homepage is a consistent issue. Although it can run through user journeys and score them on a scale of one to five, I didn’t specify the user journeys I wanted to the agent to explore. That’s a problem. How did it come up with these scenarios? Are these scenarios that a user would really take? Where did it get this information from? And where did these personas come from? It’s better for the stakeholder (or me in this case) to give specific user stories to follow.

So that’s what I decided to do next.

## User Stories in a browser

I provided the following prompt to my agent:

> 
> 
> 
> Let's get the QA agent to spin up a browser (using Preview mode) and run through the following stories:
> 
> GIVEN I am a user
> WHEN I open the homepage
> AND I type in 'Amazon' in the search box
> THEN Amazon is shown in the search results
> 
> GIVEN I am a user
> WHEN I open the homepage
> AND I type in 'Amazon' in the search box
> AND I select 'Amazon' from the list of results
> THEN the stock information page for Amazon will be displayed
> AND there is a chart showing the historical stock price
> AND there is the current stock price
> AND there is a list of news items
> AND there is an icon for Amazon

## How AI could be used in software testing

So we know that using the agent in a browser isn’t the best, but it’s excellent at exploratory testing, understanding BDD and writing automated tests. With this in mind, here is how I would approach using AI to assist with software testing:

- Provide BDD stories that demonstrate specific user journeys and behaviours
- Instruct the agent to run these stories in a browser…
- …and capture these tests by writing Playwright tests

Here’s an example of how that looks:

> 
> 
> 
> Now I have the conventions. The existing E2E tests mock the API routes with fixtures (deterministic, no live Finnhub dependency). I'll have the QA agent do the live browser run first, then write Playwright tests in that same mocked style. Let me brief it thoroughly.
> 
> Ran an agent
> The agent reports success. Let me verify the actual file and the test run before reporting back — trust but verify.
> 
> Read a file, ran a command
> The test file looks clean and follows the existing conventions. Let me independently confirm it passes rather than just trusting the agent's report.
> 
> Ran
> Run the new Amazon BDD Playwright tests
> Verified independently — both new tests pass.
> 
> Done
> Branch: chore/QA-improvements created off main and checked out.
> 
> Live browser run (Claude Preview) — both scenarios PASS
> Scenario 1 — Amazon in search results
> 
> Homepage → typed "Amazon" → dropdown showed AMZN / Amazon.com Inc ✅
> Scenario 2 — full Amazon dashboard (each AND checked separately)
> 
> Clause	Result
> Stock page is for Amazon (AMZN / Amazon.com Inc)	✅
> Historical price chart (<canvas>, "Price History")	✅
> Current price ($266.34)	✅
> List of news items ("Latest News" + headlines)	✅
> Amazon icon (<img alt="AMZN logo"> from Finnhub CDN)	✅
> A useful DOM fact the agent confirmed live: the company icon is a real <img> with alt="AMZN logo", sourced from the /api/stock/profile route's logo field — so the test asserts the right thing.
> 
> Playwright tests written
> New file: tests/e2e/amazon-bdd.spec.ts (2 tests), following the existing repo convention of mocking the API routes (page.route(...) with Amazon fixtures derived from the live data), so they're deterministic and need no Finnhub key:
> 
> searching for 'Amazon' shows Amazon in the search results
> selecting Amazon shows the dashboard with chart, price, news, and icon
> The BDD Given/When/Then is preserved as inline comments, and each Scenario-2 AND maps to its own expect() so a failure pinpoints the exact clause. The movers route is stubbed with [] to avoid the TickerTape strict-mode multi-match issue (same trick as the existing search.spec.ts).
> 
> Verification (I re-ran it myself)
> deno task test:e2e -- tests/e2e/amazon-bdd.spec.ts   →  2 passed (5.5s)
> The agent also reported the full suite green at 36 passed (34 prior + 2 new), no regressions. No app source was modified — this was test-authoring only. Nothing committed yet.
> 
> Two notes worth flagging:
> 
> The agent observed the duplicate profile fetch regression live (profile called 3+ times per dashboard load) — it doesn't affect these tests since page.route() intercepts all calls, but it's the same N-03 issue from the earlier passes.
> git status shows the new test file plus the untracked .claude/ dir (pre-existing, not mine to touch).
> 

And sure enough, it did write a new file which had the tests and included the BDD scenarios as comments. This loop of verifying the behaviour and capturing it in an automated test would bring value in creating and maintaining a regression pack.

## So, could AI take my job in software testing?

At this time of writing, *somewhat*, but not fully. I can see it being more of an assistant in helping me do my work.

Sure, it can write tests in Playwright, open a browser in Claude’s desktop application, and explore the application or follow user stories, but it is slow when watching it interact with a live browser. Plus, it can only use the browser in Claude’s desktop application and not browsers that are commonly used like Chrome, Firefox or Safari, so it’s limited in that regard.

However, it is useful in writing tests that capture user journeys and behaviours, especially if it’s writing tests for Playwright that uses actual browsers. The pipe dream of having fully automated regression testing is within reach by orchestrating a QA specific agent to write tests, maintain and add new tests as new features get added.

But where does that leave the QA specialists? Verification of these applications is still important, along with ownership of the tests that the agents generate, and doing investigations is something that a human could do faster and potentially more accurately than an agent can. Plus, these AI systems still require prompts as subject matter experts would provide accurate and relevant context.

How long this will last is uncertain. Artificial intelligence is advancing at an unprecedented rate, and the fear that it could begin replacing people in the near future is a genuine concern. I still stand by my view that the next twelve months is going to be crucial for so many people’s careers and livelihoods.

After this brief experiment, I can’t help but feel that we’re about to witness the world of work change forever.
